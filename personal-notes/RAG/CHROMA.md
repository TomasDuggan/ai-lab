# Chroma (Vector Store)

## What it is

Chroma is a vector database, not a relational database. Its core operation
is not exact-match or range queries (`WHERE genre = 'Action'`) - it's
"find the k vectors closest to this vector" (similarity/distance search).

It does use SQLite internally to persist documents and metadata, but that's
an implementation detail. The engine that actually powers search is a
vector index, structurally different from a relational B-tree index.

Chroma can run embedded (as a plain Python library, no separate server),
persisting to a local folder - no infra needed for local/small-scale use.

## Setup vs runtime

Two distinct moments, not to be confused:

- **Setup (offline, run manually or on data change):** ingestion, chunking,
  embedding generation, and inserting into Chroma. This populates the
  persistent folder on disk. Not triggered by HTTP requests.
- **Runtime (per HTTP request):** the app just *reads* from the already
  populated Chroma folder - embed the incoming query, run `collection.query()`,
  use the results. No re-ingestion, no re-chunking happens here.

The Chroma client (connection to the persistent folder) should be opened
once at app startup, not reopened per request.

## Core concepts

- **Collection**: like a "sql table" grouping a set of vectors + their metadata.
  Created once (`get_or_create_collection`).
- Each entry in a collection needs:
  - **id**: unique string. A chunk's `source_id` alone is not enough if a
    document has multiple chunks - combine `f"{source_id}_{chunk_index}"`.
  - **embedding**: the vector. Should be generated by the same model used
    everywhere else in the pipeline (see Embeddings notes on why mixing
    models breaks comparability). Don't rely on Chroma's default embedding
    function if you're already generating embeddings yourself elsewhere -
    silent model mismatch is a real risk.
  - **document**: the raw chunk text (so it can be retrieved and shown, not
    just matched against).
  - **metadata**: dict of non-embedded fields used for filtering (genres,
    developers, release_date, etc).

## HNSW

HNSW = Hierarchical Navigable Small World. The graph-based index Chroma
uses under the hood for Approximate Nearest Neighbor (ANN) search.

"All vectors compared against the query" (brute force) is exact but doesn't
scale to millions of vectors. HNSW trades a small amount of exactness for
speed: instead of comparing against every point, it navigates a precomputed
neighbor graph, giving roughly logarithmic search time instead of linear.

At small scale (hundreds of chunks), brute force and HNSW return
practically identical results - the real benefit of Chroma at this scale
isn't search speed, it's **persistence** (not recomputing embeddings every
run).

## Distance metric (`hnsw:space`)

Set when the collection is created - cannot be changed without recreating
the collection and reinserting all data.

```python
client.get_or_create_collection(
    name=COLLECTION_NAME,
    metadata={"hnsw:space": "cosine"}
)
```

If not specified, Chroma's default is **L2 (Euclidean distance)**, not
cosine. This matters a lot for interpreting results:

- With `hnsw:space="l2"`: lower value = more similar, unbounded scale.
- With `hnsw:space="cosine"`: Chroma returns **cosine distance**
  (`1 - cosine_similarity`), not similarity directly. Lower = more similar,
  roughly bounded [0, 2].

To read Chroma's cosine distance as the "familiar" similarity score:

    similarity = 1 - distance

Forgetting this conversion leads to misreading results (e.g. thinking a
distance of 0.5 means "50% similar" or interpreting mid-range distances as
bad when they're actually a normal similarity level for short text).

## Querying

```python
results = collection.query(
    query_embeddings=query_embedding,  # same model as ingestion
    n_results=5
)

for doc, meta, dist in zip(results["documents"][0], results["metadatas"][0], results["distances"][0]):
    print(meta["name"], "-", dist)
    print(doc[:150])
    print()
```

Returns `documents`, `metadatas`, and `distances` (not similarities) per
result, ordered best-to-worst according to the metric in use.

## Chunk-level search, not document-level

Chroma has no concept of "games" or documents - only individual chunk
vectors as independent points. A query compares against every chunk
separately; there's no automatic grouping by `source_id`.

Consequence: the same game can appear multiple times in a top-k result (once
per matching chunk), while other chunks from that same game may not appear
at all, even if intuitively "they should go together." Any logic like
deduplicating by game or merging all chunks from a matched game is retrieval
logic you build on top of Chroma - not something Chroma does for you.

## Deploy considerations (small-scale, free-tier)

- The Chroma persistent folder needs to exist on the server's filesystem to
  work after deploy.
- Free tiers (Render/Railway) often have ephemeral filesystems - a folder
  generated at runtime may not survive a restart/redeploy.
- At small scale (few hundred chunks), the pragmatic solution is committing
  the Chroma folder to the repo, so it ships with the code on deploy (if it's small).
- Raw/intermediate files (`games.jsonl`, `chunks.jsonl`) are regenerable and
  don't need to be committed - only the final Chroma folder does.
